# Raw Prompt 最小写作协议 v1

## 1. 文档目的

本协议用于约束项目中的 **raw prompt** 编写边界。

它的目标不是统一所有 prompt 的写法，
也不是要求固定模板或固定字段，
而是确保每一个 raw prompt 在进入系统前，至少具备基本的方法论完整性与层级干净度。

本协议解决的问题是：

- raw prompt 方法论目标不清
- raw prompt 推进逻辑松散
- raw prompt 缺少覆盖范围与收束方向
- raw prompt 与产品层、交互层、工程层混写
- 后续 PromptAdapter / PromptRunner 被迫承担过多方法论修补工作

一句话：

**raw prompt 必须先是一个成立的方法论源文件，然后才谈得上进入系统。**

---

## 2. raw prompt 的角色定位

raw prompt 只负责定义：

- 这套方法论想帮助用户完成什么
- 这套方法论如何推进
- 这套方法论至少覆盖什么
- 这套方法论如何逐步收束
- 这套方法论在执行时遵守什么工作原则

raw prompt 不负责定义：

- JSON 输出字段
- status 枚举
- 前端展示规则
- 右侧成果区逻辑
- confirmation_candidate
- blocking / non_blocking
- 用户点击后的流转
- PromptAdapter 输出协议
- PromptRunner 修补逻辑

因此必须明确：

**raw prompt 负责“怎么聊得成立”，不负责“怎么接入系统”。**

---

## 3. 协议性质

本协议是 **软协议**，不是硬模板。

这意味着：

### 允许
- 不同 raw prompt 有不同写法
- 不同 raw prompt 有不同结构顺序
- 不同 raw prompt 使用不同标题命名
- 不同 raw prompt 使用不同术语表达阶段与结果

### 不要求
- 必须写 `Phase 1 / Phase 2 / Phase 3`
- 必须写 `Role / Profile / Mission`
- 必须按固定顺序组织内容
- 必须使用统一标题
- 必须使用统一字段名

### 真正检查的不是
- 格式是否标准
- 标题是否统一
- 排版是否像模板

### 真正检查的是
- 关键信息是否可识别
- 方法论是否成立
- 层级边界是否干净

一句话：

**检查的是方法论信息是否存在，不是格式是否像标准答案。**

---

## 4. raw prompt 的最小必需信息

任意 raw prompt，在进入系统前，至少应当能被识别出以下四类信息。

---

### 4.1 方法论目标

raw prompt 必须能看出：

**这套方法论最终想帮助用户完成什么。**

要求：

- 目标必须具备工作性，而不是纯氛围表达
- 目标必须指向“帮助用户完成某种认知推进、判断收束或结果形成”
- 目标不能只停留在“陪伴”“理解”“启发”这类过虚表达

合格示例方向：

- 帮助用户识别个人价值线索
- 帮助用户看清当前真正卡点
- 帮助用户从混乱叙述中收束出关键判断
- 帮助用户形成下一步可行动方向

不合格倾向：

- 做一个懂用户的人
- 给用户陪伴感
- 让用户感觉被理解
- 进行开放式自由交流

说明：

这些表达不是绝对不能出现，
但如果只有这些，而没有明确工作目标，
则方法论目标视为不足。

---

### 4.2 阶段性推进逻辑

raw prompt 必须能看出：

**这不是随机聊天，而存在阶段推进或收束路径。**

要求：

- 至少能识别出从前到后的方法论推进
- 不要求明确写阶段编号
- 但必须让人能复述出“大致怎么往前走”

可接受的推进表达包括但不限于：

- 先探索，再聚焦
- 先理解，再判断
- 先发散，再收束
- 先确认事实，再形成结论
- 先识别线索，再提出建议

不合格倾向：

- 全文只有零散要求，没有推进顺序
- 全文只有问答氛围，没有方法路径
- 全文同时要求探索、判断、建议、报告，却没有先后关系

说明：

没有推进逻辑，raw prompt 很容易退化成“看起来很深，实际很散”。

---

### 4.3 关键覆盖内容

raw prompt 必须能看出：

**这套方法论至少覆盖哪些核心问题域。**

要求：

- 至少有核心覆盖意识
- 不要求统一维度名
- 不要求列成清单
- 但必须能识别出“这套方法论重点看什么”

可接受的覆盖方向包括但不限于：

- 资源 / 限制 / 经验 / 动机
- 优势 / 阻力 / 状态 / 现实约束
- 身份感 / 方向感 / 价值感 / 行动条件
- 行为线索 / 情绪反应 / 能量变化 / 重复主题

不合格倾向：

- 全部靠临场发挥，没有核心关注面
- 只有抽象表达，没有内容抓手
- 只说“深入挖掘”，但不说明挖什么

说明：

没有覆盖内容，方法论就容易只剩气质，不剩结构。

---

### 4.4 阶段 / 流程产出方向

raw prompt 必须能看出：

**这套方法论在某个阶段或整个流程中，会形成什么类型的结果。**

要求：

- 至少存在整体产出方向
- 更优情况是同时存在阶段产出方向
- 产出不要求已经工程化，但必须语义上可识别

可接受的产出包括但不限于：

- 价值线索
- 初步判断
- 关键矛盾
- 阶段总结
- 行动方向
- 结构化发现
- 下一步优先验证点

不合格倾向：

- 全文强调持续对话，但没有任何收束概念
- 只要求不断追问，没有结果形成方向
- 只有“继续聊”，没有“聊到什么程度算形成结果”

说明：

没有产出方向，系统后续无法判断何时收束，也无法判断收束成什么。

---

## 5. 推荐补足信息

以下内容不是硬底线，
但强烈建议 raw prompt 具备。
缺失时不一定判为不可用，
但通常会影响质量、稳定性与后续系统接入成本。

---

### 5.1 阶段名称清晰度

建议 raw prompt 让阶段边界较容易被识别。

不要求：

- 固定写“第一阶段 / 第二阶段”
- 固定写统一标题

建议达到的效果是：

即使不写阶段编号，
阅读者仍能识别哪里是探索，
哪里是聚焦，
哪里是判断，
哪里是收束。

---

### 5.2 每阶段目标可见性

建议 raw prompt 不只是有推进顺序，
还让每个阶段“在干什么”能够被看见。

例如：

- 这一段主要是确认事实材料
- 这一段主要识别反复出现的信号
- 这一段主要不再扩展，而开始收束判断

没有阶段目标时，
阶段虽然存在，
但方法功能不明确。

---

### 5.3 方法论约束明确度

建议 raw prompt 明确关键工作原则。

例如：

- 一次只推进一个关键问题
- 不急于给建议
- 不直接把用户硬塞进预设类型
- 先理解，再判断
- 先建立判断，再提出行动方向

说明：

方法论约束越清楚，
不同模型、不同执行轮次的漂移越小。

---

### 5.4 阶段级产出清晰度

建议 raw prompt 不只定义最终结果，
也定义中间阶段会形成什么。

例如：

- 初步线索
- 阶段判断
- 当前核心矛盾
- 暂时不成立的假设
- 优先验证方向

说明：

阶段级产出越清楚，
后续系统越容易沉淀中间对象。

---

### 5.5 阶段产出可转译性

建议 raw prompt 的结果语义上天然容易转成中间对象。

例如：

- finding
- signal
- judgement
- tension
- action_direction

注意：

这里说的是 **语义上可转译**，
不是要求 raw prompt 直接写 JSON 字段。

---

## 6. 明确禁止的混层内容

raw prompt 最大风险之一，不只是缺信息，而是混层。

以下三类内容原则上不应写入 raw prompt。

---

### 6.1 产品展示规则

禁止写入 raw prompt 的典型内容：

- 右侧展示什么
- 展示几条
- 哪些可以点击
- 哪些高亮
- 哪些需要用户确认
- 页面如何呈现
- 卡片结构如何显示
- UI 交互如何反馈

原因：

这些属于产品层，不属于方法论层。

---

### 6.2 交互状态规则

禁止写入 raw prompt 的典型内容：

- confirmation_candidate
- blocking / non_blocking
- 用户不点击怎么办
- 状态切换条件
- 回流规则
- 用户确认后下一步如何跳转
- 哪种交互属于暂停态或继续态

原因：

这些属于系统交互层，不属于方法论层。

---

### 6.3 工程输出协议

禁止写入 raw prompt 的典型内容：

- JSON 字段
- 输出 schema
- 固定 status 枚举
- PromptAdapter 字段结构
- PromptRunner 解析要求
- parser 兼容逻辑
- 前端必须接收什么字段

原因：

这些属于工程协议层，不属于方法论层。

---

## 7. raw prompt 的实际判断标准

以后评估一个 raw prompt，不优先看它是否“像模板”，
而优先看以下五个问题。

### 7.1 目标能不能一句话说清
如果不能，说明方法论目标本身还散。

### 7.2 推进路径能不能被复述
如果不能，说明只是堆话术，不是方法论。

### 7.3 覆盖范围能不能被识别
如果不能，说明方法没有稳定抓手。

### 7.4 收束结果能不能被预期
如果不能，说明系统很难稳定接入。

### 7.5 层级边界是否干净
如果不干净，后续维护成本一定上升。

---

## 8. 接入前最低要求

任意 raw prompt 在进入系统前，至少满足以下条件：

### 必需项底线
- 方法论目标可识别
- 阶段推进逻辑可识别
- 关键覆盖内容可识别
- 产出方向可识别

### 越界底线
- 不应存在明显产品展示规则混入
- 不应存在明显交互状态规则混入
- 不应存在明显工程协议规则混入

### 总体要求
- raw prompt 至少应能被判断为“方法论骨架成立”
- 若仅有氛围、角色感、风格要求，而无方法骨架，不应直接接入系统

---

## 9. 与其他层的分工关系

### 9.1 raw prompt
负责：
- 方法论目标
- 方法推进
- 覆盖范围
- 阶段与收束
- 方法约束

### 9.2 PromptAdapter
负责：
- 输入上下文统一
- 输出协议统一
- 字段约束
- 系统接入适配

### 9.3 PromptRunner
负责：
- 执行流程
- 结果解析
- 基础护栏
- 运行时修补
- 输出标准化

因此必须避免：

- raw prompt 替 adapter 定协议
- raw prompt 替 runner 写护栏
- adapter 替 raw prompt 补方法论
- runner 长期替 raw prompt 补结构漏洞

---

## 10. 本协议的使用方式

本协议用于以下场景：

### 10.1 编写新 raw prompt 前
先对照本协议，确保最小骨架存在。

### 10.2 新 raw prompt 入库前
先进行方法论检查，确认是否适合接入。

### 10.3 老 raw prompt 迭代时
检查是否补强了目标、推进、覆盖、产出，
以及是否引入了新的混层问题。

### 10.4 讨论系统问题时
优先先判断问题属于哪一层：
- raw prompt 层
- adapter 层
- runner 层
- 产品层

避免混着改。

---

## 11. 本协议当前版本的适用边界

本协议是 v1，当前特点是：

- 偏保守
- 偏最小化
- 偏方法论底线
- 不追求覆盖所有高级 prompt 设计问题

它当前主要解决的是：

- raw prompt 没骨架
- raw prompt 混层
- raw prompt 不适合直接入系统

它暂不解决：

- 更细粒度阶段建模
- 多方法论组合 prompt 的高级规范
- 自动重写 raw prompt
- 跨任务类型的复杂评分体系

---

## 12. 当前版本的一句话原则

**raw prompt 可以自由写，但必须让人看得出它在解决什么、怎么推进、覆盖什么、如何收束，并且不要越界替系统写产品逻辑和工程协议。**
